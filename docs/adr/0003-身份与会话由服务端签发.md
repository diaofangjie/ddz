# 0003. 身份与会话由服务端签发，客户端不再自报

- **状态**：已采纳
- **日期**：2026-09-15
- **决策者**：项目负责人 + 开发

## 背景

当前系统的身份机制是**客户端自报**：

1. 玩家进入时自己输入昵称，`playerId` 由客户端生成并保存在 localStorage（见 `断线重连说明.md`）。
2. 所有动作事件都直接采信 payload 里的 `playerId`：
   `index.js:491`(doubling)、`505`(discard)、`519`(callLandlord)、`534`(playCards)、`554`(pass)。
3. `RoomManager.joinRoom`（`RoomManager.js:81`）用 **`p.name === player.name`** 匹配玩家 —— **昵称即身份**。
4. 服务端**不校验** socket 与 player 的绑定关系。

**后果**：
- 改一个字段即可替他人出牌；
- 知道对方昵称即可顶替其身份重连（`断线重连说明.md` 明确说"必须使用相同的玩家名"）；
- 配合"手牌全量广播"，可完全操控牌局。

## 决策

**身份与会话由服务端签发并绑定到 socket。**

### 握手协议

```
客户端连接
   │
   ├─ 客户端无 token：
   │     服务端签发 sessionToken（不可猜的随机串）+ playerId
   │     客户端存 localStorage
   │
   └─ 客户端带 token：
         服务端校验 → 恢复 playerId 与所在房间 → 恢复座位

所有动作事件：payload 不再包含 playerId
服务端统一从 socket.data.playerId 取身份
```

### 具体规则

1. `sessionToken` 使用 `crypto.randomUUID()` 或 `crypto.randomBytes(32).toString('base64url')` 生成，**不可预测**。
2. 服务端维护 `Map<sessionToken, { playerId, roomId, seatIndex }>`，与 socket.data 同步。
3. **昵称降级为纯展示字段**，不再参与任何身份匹配。
4. 所有 handler 开头统一校验：`AUTH_REQUIRED` / `NOT_IN_ROOM` / `NOT_YOUR_TURN` / `PHASE_MISMATCH`。
5. 重连时凭 token 恢复座位，**不再要求"输入相同昵称"**。
6. token 有效期与清理：房间销毁或玩家主动退出时失效；长期不活跃 token 定期清理。

### 破坏性变更

这是**协议不兼容变更**，对应版本号 `proto: 1 → 2`，主版本号升级（`v1.x.x → v2.0.0`）。
需要在 `02-通信协议规范.md` 中同步标注所有 🎯 条目。

## 备选方案

| 方案 | 优点 | 缺点 | 为何未采用 |
|------|------|------|-----------|
| **A. 服务端签发 token + socket 绑定（采纳）** | 无需注册，好友场景零负担；根治伪造 | 需要一次协议破坏性变更 | — |
| B. 完整账号体系（注册/登录/密码） | 身份最强、可跨设备 | 好友娱乐场景**过重**；增加注册流失、密码找回、风控等一堆工作 | 收益与成本严重不匹配 |
| C. 微信/QQ 登录 | 体验好、天然实名 | 需企业主体资质与平台审核，个人项目走不通 | 不可行 |
| D. 维持现状，仅在前端隐藏 `playerId` | 零改动 | 与"手牌隐藏"一样是纸糊的，抓包即破 | 无效 |
| E. 昵称 + 简单口令 | 改动小 | 口令管理、泄露、重放问题一堆；本质还是自报 | 不如 A 干净 |

## 后果

### 正面
- 伪造身份、顶替他人彻底不可行
- 重连体验改善：**不再要求用户记住并输入完全一致的昵称**
- `playerId` 从所有 payload 中消失 → 协议更简洁，客户端更难"作恶"
- 为后续"战绩体系"提供稳定主键（当前 `playerId` 由客户端生成，不可信，无法作为统计主键）

### 负面 / 需要接受的成本
- **协议破坏性变更**：前后端必须**同版本发布**，存在短暂的版本错配风险（建议服务端兼容旧客户端一个版本，握手时按 `proto` 字段分支）
- 前端需要新增握手逻辑与 localStorage 管理
- 服务端需要维护 token 存储与清理（内存即可，不需要 DB）

### 中性
- 清 localStorage 会丢失身份 → 需要接受"换浏览器即新玩家"（好友场景可接受），并在 UI 上给出提示
- 未来若要做账号体系，可在 `sessionToken` 之上叠加，不需要推翻
