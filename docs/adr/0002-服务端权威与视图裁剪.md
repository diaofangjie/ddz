# 0002. 采用服务端权威 + 按观察者视图裁剪

- **状态**：已采纳
- **日期**：2026-09-15
- **决策者**：项目负责人 + 开发

## 背景

当前服务端通过 `serializeRoom(room)`（`server/src/index.js:119-143`）把房间对象**原样**发送给房间内所有人，其中包含 `room.game` 全量字段 —— **包括 `game.hands`，即所有玩家的手牌**。

调用点：`index.js:146 / 431 / 493 / 507 / 521 / 539 / 556` 等。

**后果**：任何玩家打开浏览器 DevTools → Network → WS，即可实时看到对手手牌与底牌，牌局完全失去意义。

这在"好友娱乐"场景下被长期忽略，但一旦要"优化成可持续的项目"，就是必须解决的架构级缺陷。
同时，`serializeRoom` 并非唯一出口 —— 另有 16 处直接 `emit('gameUpdated', currentRoom)` 传原始对象（含 `Set` 类型的 `readyPlayers`），导致状态形状不一致，产生偶发 bug。

## 决策

1. **服务端权威（Server-Authoritative）**：客户端只发送"意图"（我想出这几张牌 / 我想叫 2 分），一切状态判定与变更由服务端完成，客户端永不参与判定。

2. **按观察者视图裁剪（Per-Viewer Projection）**：服务端不再广播"房间对象"，而是为**每个连接单独生成**它有权看到的状态。

```js
function projectFor(room, viewerId) → ViewState
```

3. **单一广播出口**：新增 `broadcast(room)`，内部完成"逐人投影 → 单发"，并**删除全部裸 `emit(..., currentRoom)`**（16 处）。

4. **房间对象不允许直接序列化出进程**：开发期加断言防止复发。

## 字段可见性规则

| 字段 | 自己 | 其他玩家 | 观战者 |
|------|------|----------|--------|
| 自己的手牌牌面 | ✅ 完整 | — | — |
| 他人手牌 | ⚠️ 仅张数 | ⚠️ 仅张数 | ⚠️ 仅张数 |
| 底牌 | 抢地主结束前 ❌ | 抢地主结束前 ❌ | ❌ 全程 |
| 已出牌堆 | ✅ | ✅ | ✅ |
| 分数 / 倍数 / 局数 / 当前行动者 | ✅ | ✅ | ✅ |
| socket id / sessionToken / 定时器句柄 | ❌ 永不外发 | ❌ | ❌ |

## 备选方案

| 方案 | 优点 | 缺点 | 为何未采用 |
|------|------|------|-----------|
| **A. 逐人投影后单发（采纳）** | 手牌天然不出服务端，无法绕过；观战席/队友视角都可自然扩展 | 每房间每次广播要做 N 次投影（N ≤ 10，成本可忽略） | — |
| B. 保持全量广播，客户端自行隐藏 | 改动最小 | **毫无意义** —— 数据已在客户端，抓包即得，等于没做 | 治标不治本 |
| C. 分频道（每人一个 room，只发自己的） | 简单直观 | 公共状态要发 N 次且容易漏；阶段切换时状态一致性难保证 | 与 A 相比没有优势，A 是 C 的规范化版本 |
| D. 增量差分同步 | 流量最小 | 实现复杂度高，易产生"状态漂移"类难查 bug | 10 人规模无此必要（YAGNI） |

## 后果

### 正面
- 作弊面被彻底消除：**数据从未离开服务端**
- 观战席、队友观牌等后续需求可零成本扩展
- 消除"两条广播路径"导致的状态不一致 bug（P1-1）
- 为后续加"提示可出牌"（`game:hint`，服务端算）铺路

### 负面 / 需要接受的成本
- 每次广播要做 N 次投影与 N 次 `emit`（N ≤ 10，实测可忽略）
- 前端需要适配新的状态形状（`seats[].hand` 只对自己存在）→ 需同步改 `client/src/App.js` 与 `GameScreen.js`
- 过渡期需要**同时**维护新旧两种下发方式，直到前端切换完成

### 中性
- 这是实时对战类应用的行业标准做法（权威服务端 + 兴趣管理）
- 若未来单机房间数达千级，可加"相同视图分组"优化 —— 当前明确不做
