# 0001. 保留 Node + Socket.IO，做外科手术式重构而非重写

- **状态**：已采纳
- **日期**：2026-09-15
- **决策者**：项目负责人 + 开发

## 背景

现有系统（`D:\dfj\dfj\ddz`，1881 行后端 + 约 2000 行的 `GameScreen.js`）已具备：

3 人/4 人斗地主、癞子（`normal` / `tiandi`）、加倍与超级加倍、封顶倍数、弃牌阶段、2v2 红蓝队伍、局数选择（4/8/16）、文字聊天、断线重连、离线 AI 托管、记牌器、PWA、Capacitor 移动端打包。

这些玩法细节**全部是自研实现**，没有现成库可以替代。同时系统存在明确的架构问题（见 `00-现状审计与风险清单.md`）：

- 手牌全量广播（可作弊）
- 客户端自报身份（可伪造）
- 超时/托管/AI 三段逻辑重复
- 两个巨型文件（`index.js` 543 行、`GameScreen.js` 81.8 KB）
- 无版本控制、无测试

需求方希望"优化或重构"，并实现"实时多人在线对战（≤10 人）"。

当前系统已在阿里云线上运行（`8.137.195.155`，服务健康）。

## 决策

**保留 Node.js + Express + Socket.IO + React 的技术栈，采用绞杀者模式（Strangler Pattern）渐进重构。**

具体含义：
1. **不换技术栈主干**。不引入 TypeScript 重写、不迁 Go/Rust、不换通信框架。
2. **不重写业务逻辑**。现有玩法规则作为资产保留，只做"抽取 + 测试 + 修正"。
3. **新旧模块并存**，逐个把调用切过去；每个子任务独立提交、独立可回滚。
4. **技术栈的局部升级可以单独决策**（如 CRA → Vite），但必须另开 ADR，且不与架构重构混在同一次改动里。

## 备选方案

| 方案 | 优点 | 缺点 | 为何未采用 |
|------|------|------|-----------|
| **A. 绞杀者式渐进重构（采纳）** | 风险可控、随时可停、玩法细节不丢、线上不中断 | 重构期较长，会有一段"新旧并存"的过渡态 | — |
| B. 从零重写 | 架构最干净、无历史包袱 | ①10+ 项自研玩法要重踩坑；②重写期线上无新功能；③历史 bug 与新 bug 叠加，回归面不可控；④该项目是好友娱乐，投入产出比极低 | 成本远高于收益 |
| C. 只做表面优化（修 bug 不改架构） | 最省力 | 核心问题（可作弊、逻辑重复）不解决，后续每加一个功能都会更痛 | 无法满足"可持续优化"的目标 |
| D. 换用成熟游戏服务端（Colyseus 等） | 自带房间/状态同步 | 需改写全部玩法逻辑；且斗地主的"座位 + 阶段状态机"用通用框架反而更绕 | 迁移成本 ≈ 重写 |

## 后果

### 正面
- 现有 10+ 项玩法能力**零丢失**
- 任意阶段可停下来交付一个"比之前更好"的版本，不会出现"半成品"
- 每一步都能回滚（配合阶段 0 建立的 git）
- 测试网一旦建立，后续所有迭代都受益

### 负面 / 需要接受的成本
- 过渡期会短暂存在"新旧两套逻辑"，需要严格约束调用方向（新模块可以调旧模块，反之禁止）
- 需要维护 git 分支纪律与提交粒度，不能一次提交一大坨
- 重写能带来的"彻底整洁"永远不会完全达成，会长期保留一些历史包袱

### 中性
- 这是行业内处理"有历史包袱但业务正常"的系统的主流做法
- 前端 CRA 已停止维护，长期看仍需迁 Vite（单独立项，不在本次范围）
