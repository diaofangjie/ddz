## 2. 风险清单

严重度：🔴 P0 阻断/安全 · 🟠 P1 严重 · 🟡 P2 改善

### 🔴 P0-1 项目没有版本控制【实测】

`D:\dfj\dfj\ddz\.git` **不存在**，但存在 `.gitignore`。目录里还混着 `client/build/`（构建产物）、`ddz-alibaba-deploy.zip`、`repomix-output.xml`。

**风险**：任何重构都不可回滚，一次误删即灾难。这是所有工作的**前置阻断项**。
**处理**：`git init` → 补全 `.gitignore` → 首次全量提交 → 打 tag `v1.0.0-baseline`（详见 06 文档阶段 0）。
**状态**：✅ **已修复**。已 `git init` 并补全 `.gitignore`（排除 `build/`、`*.zip`、`repomix-output.xml`、`.vercel/`、`data/*.json` 等）；远端 `origin` 指向 `github.com/diaofangjie/ddz.git`；基线提交 `de86ed9` 已落在远端 `13cf9bf`（Initial commit）之上。（仅"推送到远端"待用户授权凭据，见第 6 节。）

### 🔴 P0-2 手牌全量广播（可作弊）【实测】

`server/src/index.js:119-143` 的 `serializeRoom()` **原样保留了 `room.game` 全量字段**（含 `game.hands` = 所有玩家手牌），随后在 `index.js:146 / 431 / 493 / 507 / 521 / 539 / 556` 等处通过 `io.to(room.id).emit(..., serializeRoom(room))` 发给了**房间内所有人**。

**风险**：任何玩家打开浏览器 DevTools → Network → WS，即可实时看到对手手牌与底牌。对"好友娱乐"是体验问题，对"要优化成可持续项目"是**架构级缺陷**。
**处理**：引入**视图裁剪** `projectFor(room, viewerId)`，见 `01-目标架构设计.md` 第 3 节。
**状态**：✅ **已修复**。`index.js` 新增 `hiddenCards()` / `projectGame()` / `serializeRoom(room, viewerId)`，广播改为 `emitPerViewer()` 单一出口：每个观察者收到的 `game.hands` 中**只有自己是真实牌**，其余为等长占位牌（`rank:'hidden'`，前端只用其 `length`）；底牌在地主确定前不下发。端到端测试已断言"全程无手牌泄露"。

### 🔴 P0-3 客户端自报身份（可伪造）【实测】

所有动作事件都直接采信 payload 里的 `playerId`：`index.js:491`(doubling)、`505`(discard)、`519`(callLandlord)、`534`(playCards)、`554`(pass)。服务端**不校验 socket ↔ player 的绑定关系**，也不校验"是否轮到你"。

**风险**：改一个字段就能替别人出牌；配合 P0-2 可完全操控牌局。
**处理**：身份改由服务端签发并与 socket 强绑定，见 P0-4 与 ADR-0003。
**状态**：✅ **已修复**。新增 `authorize(socket, roomId)`，身份一律取自 `socket.data.playerId` 或 `roomManager.getPlayerIdBySocket(socket.id)`，**payload 里的 `playerId` 被彻底忽略**；`RoomManager` 增加 `bindSocket/getPlayerIdBySocket/getSocketIdsByPlayer` 维护映射，并新增"同一 playerId 只保留最新 socket"的收敛逻辑。端到端测试已断言"伪造他人 playerId 出牌被拒绝"。

### 🔴 P0-4 无会话/令牌机制【实测 + 推断】

`断线重连说明.md` 明确要求"必须使用**完全相同的玩家名**"才能重连，`playerId` 由客户端生成并存在 localStorage。

**风险**：名字即身份 → 抢注他人昵称即可顶替；玩家 ID 可任意伪造。
**处理**：首次连接由服务端签发 `sessionToken`（随机不可猜），客户端持久化，重连时凭 token 恢复身份。
**状态**：🟡 **部分修复**。"名字即身份"这一条已彻底铲除：`RoomManager.joinRoom` 中"同名即重连"的分支被删除，只认 `p.id === player.id`。完整 `sessionToken` 机制（服务端签发+持久化）尚未落地，仍列在迭代路线图阶段 0。

### 🔴 P0-5 无 HTTPS（443 未开放）【实测】

前端 `http://` 分享、Socket.IO 走明文 `ws://`。
**风险**：微信/部分移动浏览器对 `http` 站点限制（麦克风、通知、剪贴板等 API 不可用，分享卡片降级）；流量可被监听篡改；无证书无法上 CDN/域名。
**处理**：申请域名 → Nginx 终结 TLS → 反代 `/socket.io` 到 3001，见 `04-部署与运维手册.md`。

### 🔴 P0-6 状态无持久化【实测】

房间与对局全部在进程内存 Map 中（`RoomManager`），无快照、无落库。
**风险**：`pm2 restart`、进程 OOM、服务器重启 → 所有进行中的对局瞬间消失；无法做战绩、无法复盘。
**处理**：定期快照 + 对局结束后落库（SQLite 起步），见 `01-目标架构设计.md` 第 7 节。

### 🟠 P1-1 广播路径不一致（真实 bug）【实测】

代码里有两条并行路径：

- 路径 A（**未序列化**）：`index.js:75 / 80 / 85 / 91 / 103 / 259 / 264 / 269 / 275 / 290 / 302 / 352 / 359 / 365 / 382 / 389` 直接 `emit('gameUpdated', currentRoom)` 传**原始对象**。
- 路径 B（**已序列化**）：其余位置传 `serializeRoom(room)`。

原始对象里 `readyPlayers` 是 `Set`，`JSON.stringify` 后变成 `{}`；`matchHistory` 里的数组也可能带非标准结构。

**风险**：客户端在超时/AI 触发路径下收到 `readyPlayers: {}`，`Array.isArray` 判断失败 → 准备状态显示错乱、下一局无法开始等偶发 bug。这类"偶发"最难查。
**处理**：统一为**单一出口** `broadcast(room)`，见 `01-目标架构设计.md` 第 4 节。
**状态**：✅ **已修复**。16 处 `emit(currentRoom)` 已全部收敛到 `emitPerViewer/broadcastRoomState/broadcastGameState/broadcastGameStarted`；`serializeRoom` 强制把 `readyPlayers` 归一为数组。端到端测试已断言"`readyPlayers` 为数组"。

### 🟠 P1-2 客户端发出的事件服务端没有实现【实测】

`client/src/App.js:290` 发送 `voteExtend`（延长局数投票），但服务端 `index.js` 的 `io.on('connection')` 中**没有 `voteExtend` 的 handler**（已全量检索确认）。

**风险**：用户点了按钮界面无反应、无报错 —— 静默失效的功能。
**处理**：要么补齐实现，要么移除入口。记入路线图阶段 4 需求池。

### 🟠 P1-3 超时 / 离线托管 / AI 三段逻辑重复【实测】

同一套"按阶段决定默认动作"的逻辑被写了三遍：

- `startTurnTimer()` — `index.js:50-116`
- `handleOfflinePlayerAction()` — `index.js:241-314`
- `handleAIAction()` — `index.js:322-399`

每段都硬编码了 `calling / doubling / discarding / playing` 四个分支。

**风险**：新增一个阶段（或改 4 人局规则）要改三处并保证三处一致，是**后续迭代最大的事故源**。
**处理**：抽成单一 `defaultActionFor(phase, seat)` + 统一调度器 `advance(room)`，见 `01-目标架构设计.md` 第 5 节。
**状态**：✅ **已修复**。三处重复分支已合并为唯一实现 `applyDefaultAction(room, player)`，超时/AI/离线托管共用。另外在其"跟牌"分支加了兜底：AI 返回的牌若被规则层判为压不过上家，一律降级为过牌，保证**状态机永远能推进**（这曾是一个真实卡死点，见第 6 节 BUG-1）。

### 🟠 P1-4 递归 + setTimeout 取代调度器【实测】

`handleAIAction` 内部递归调用自身（`index.js:353/360/366/383/390`），每个动作后 `setTimeout(1000)` 再触发。代码中已出现"重新检查 room / currentPlayer 是否变化"的补丁注释（`index.js:252-254 / 342-344`），说明竞态已经真实发生过。

**风险**：长局下调用链变深、多房间并发时行为不可预测。
**处理**：改为"动作完成 → 触发一次 `advance()`"的单向调度。

## 5. 审计结论

| 维度 | 评价 |
|------|------|
| 功能完整度 | 🟢 高。3/4 人玩法、癞子、加倍、弃牌、队伍、托管、重连均有实现 |

正确策略不是重写（重写的代价远高于收益，且现有玩法细节会大量丢失），而是：
**先用版本控制兜底 → 再补安全与测试 → 然后按模块渐进重构 → 最后叠加在线规模能力。**

| **BUG-1** | 离线托管/AI 自动出牌抛 `要压过上家的牌才可以呀~`（`PLAY_TOO_SMALL`），整局卡死 | `aiDecidePlayCards` 的**炸弹分支没有做合法性校验**（`single`/`pair` 分支校验了），双副牌模式下对手可能是 5~8 张炸弹，无条件返回 4 张同点压不过 | 新增 `pickBomb()`，所有候选炸弹经 `evaluateHand` + `compareHands` 校验后才返回，否则返回 `null`（过牌）；`applyDefaultAction` 再加一层 try/catch 兜底 |
| **BUG-2** | 在叫地主/加倍/弃牌阶段也能通过 `playCards` 事件改动手牌 | `handlePlayCards` / `handlePass` 缺少 `phase !== 'playing'` 校验 | 两个入口都在最前面补上阶段校验 |
| **BUG-3** | 计分不守恒（`sum(scores) ≠ 0`），长期对局分数整体漂移 | 胜方收益"取整后再除以人数"、败方各自取整，个人加倍倍数不一致时产生误差 | `calculateScores` 改为**零和奖池模型**：输家各付「基础分 × 自己的倍数」入池，池按赢家权重分配，余数给权重最高者，保证严格零和 |
| **BUG-4** | 全员不叫地主时牌局无法正常开局 | 用 `Math.random()` 触发且硬编码 `landlord=0` 但 `currentPlayer=1`，状态自相矛盾 | 新增 `callPasses` 计数，全员放弃时**强制 0 号位为地主、1 分**，并同步 `currentPlayer` |
| **BUG-5** | 4 人局加倍结束后 `currentPlayer` 可能为 `null` 导致崩溃 | 4 人局无地主，代码却统一取 `game.landlord` | 按人数分支：3 人局回到地主，4 人局取 `currentPlayer % players.length` |
| **BUG-6** | 4 人局红蓝队伍人数可能不是 2v2 | 分队依赖随机，未做兜底 | `startGame` 结束时校验红蓝各 2 人，不足则随机重排补齐 |
| **BUG-7** | 记牌器在 4 人变体里显示 8 张"幽灵 3"；地主视角底牌被重复扣减出现负数 | 记牌器按固定 15 档牌面计算；底牌既在 `myHand` 又在 `dipai` 里各扣一次 | 4 人模式下将 `3` 档置 0 并从渲染列表移除；底牌仅对**非地主**扣减（地主手牌已含底牌） |
| **BUG-8** | 底牌在地主确定后仍与地主手牌重复存在（`dipai` 未清空，仅影响展示观感） | 叫地主时把底牌并入地主手牌，但未清空 `dipai` | 保留为"明牌展示"用途，已确认前端按"底牌区 + 手牌区"分别渲染，无计数错误 |

### 6.3 测试网（对应 P1-6）
