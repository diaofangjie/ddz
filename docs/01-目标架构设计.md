# 01 - 目标架构设计

> 设计目标：在不推倒重来的前提下，把当前"能跑"的系统，改造成"敢改、能扩、可测、防作弊"的系统。
> 本文是重构的**唯一架构依据**，任何模块划分不得绕过本文。

---

## 1. 设计原则

| 原则 | 含义 | 对应修复 |
|------|------|----------|
| **权威服务端** | 客户端只发送"意图"，一切状态变更由服务端裁定；客户端永远不参与判定 | P0-3 |
| **按需视图** | 每个连接只收到"它有权看到"的最小状态，手牌天然不出房间 | P0-2 |
| **身份由服务端签发** | `playerId` 不接受客户端输入，凭 `sessionToken` 恢复 | P0-4 |
| **单一出口** | 每个房间只有一条广播路径，杜绝"两条路两个形状" | P1-1 |
| **单向调度** | 状态机推进只走一个 `advance()`，禁止递归自调用 | P1-3 / P1-4 |
| **规则纯函数化** | 牌型判定/比较/可出牌枚举不碰 IO、不碰随机源、可确定性测试 | P1-6 |
| **渐进可分** | 每个模块都能单独替换/测试，避免"必须整体换" | P1-5 |

## 3. ★ 核心机制一：视图裁剪（防作弊的地基）

**问题**：`serializeRoom()` 把 `game.hands`（所有人手牌）广播给全房间。

**设计**：服务端不再广播"房间对象"，而是广播"**针对某个观察者的投影**"。

```js
/**
 * 生成某一观察者可见的房间状态
 * @param {Room} room
 * @param {string} viewerId  玩家 id；观战者传 'spectator'
 */
function projectFor(room, viewerId) { /* 见下方字段表 */ }
```

**字段可见性矩阵**：

| 字段 | 自己 | 其他玩家 | 观战者 |
|------|------|----------|--------|
| 我的手牌（牌面） | ✅ 完整 | ❌ | ❌ |
| 他人手牌 | ⚠️ 仅**张数** | ⚠️ 仅**张数** | ⚠️ 仅**张数** |
| 底牌（`bottomCards`） | 抢地主结束前 ❌，之后 ✅ | 同左 | ❌ 全程 |
| 已出牌堆（`playedCards`） | ✅ | ✅ | ✅ |
| 当前行动者 / 剩余秒数 | ✅ | ✅ | ✅ |
| 分数、倍数、局数 | ✅ | ✅ | ✅ |
| 座位昵称/头像/在线状态 | ✅ | ✅ | ✅ |
| `sessionToken` / 内部定时器句柄 | ❌ **永不外发** | ❌ | ❌ |

**广播方式**：由"一次广播给一群人"改为"**逐人投影后单发**"。

```js
// 目标：单一出口
function broadcast(room, event = 'room:state') {
  for (const c of room.connections()) {
    c.socket.emit(event, projectFor(room, c.viewerId));
  }
}
```

> 性能说明：单房间 ≤10 人，逐人投影的成本可忽略（每次投影是浅拷贝 + 一次 `map`）。
> 若未来单机房间数上千，可加"相同视图分组"优化，但现在**不需要**（YAGNI）。

**验收标准**：在浏览器 DevTools 的 WebSocket 帧里全量搜索，**不应出现任何非本人牌面的 `suit`+`rank` 组合**。

## 4. ★ 核心机制二：单一广播出口

**问题**：`io.to(roomId).emit('gameUpdated', currentRoom)`（原始对象，`Set` 变 `{}`）与 `serializeRoom(room)` 两条路径并存。

**设计**：
- 删除所有裸 `emit(..., currentRoom)`。
- 唯一出口 `broadcast(room)`，内部完成 投影 → 发射。
- 房间对象**不允许直接离开服务端进程**（加一层 `assertSerializable` 开发期断言，防止有人再犯）。

**验收标准**：`grep -rn "emit('gameUpdated', currentRoom" server/src` 结果为空。

## 5. ★ 核心机制三：统一调度器（消灭三份重复逻辑）

**问题**：超时、离线托管、AI 三段逻辑各写了一遍四阶段分支。

**设计**：把"推进一局"抽象为**一个函数**。

```js
// room/scheduler.js
/**
 * 推进房间状态机：
 *  1. 若当前阶段已满足推进条件 → 由 machine 推进
 *  2. 广播新状态
 *  3. 若当前轮到 AI / 离线玩家 → 排一个定时任务，到点执行默认动作后再次 advance()
 *  4. 若当前轮到真人 → 启动回合计时器，超时执行默认动作后再次 advance()
 */
function advance(room) { /* 单一入口，禁止任何其他路径直接改 phase */ }
```

- **默认动作**统一为 `defaultActionFor(phase, seat, rules)`：
  - `calling` → 不叫（0 分）
  - `doubling` → 不加倍
  - `discarding` → 不弃牌
  - `playing` → 有压制牌则出最小压制，否则 pass（必须出牌时出最小单张）
- 定时器句柄统一存在 `room.timers`，`advance` 开头先 `clearAll(room.timers)`。
- **禁止**在 AI/超时处理里递归调用自身。

**收益**：新增"抢地主""明牌""翻倍"等阶段时，只需在 `machine.js` 的转移表加一行 + `defaultActionFor` 加一个 case。

## 6. 座位模型（支撑 ≤10 人房间）

```
Room {
  id: string
  rules: { mode: 3|4, laizi: bool, capMultiplier: number, rounds: 4|8|16, turnTimeLimit: sec }
  seats: Seat[]            // 长度 = rules.mode（3 或 4）
  spectators: Connection[] // 观战连接
  capacity: 10             // 房间总容量（含观战）
  phase: Phase
  ... 对局状态
}

Seat {
  index: number
  playerId: string | null
  name, avatar
  ready: boolean
  connection: Connection | null   // 与 socket 绑定；null 表示离线
  isBot: boolean                  // 托管中
  score: number
}
```

**人数语义（重要澄清）**：斗地主是 3 或 4 人对局，"最多 10 人"应理解为：

- **方案 A（推荐）**：房间总容量 10 = N 个座位（3 或 4）+ 最多 6~7 个**观战席**。轮换时观战者可"上座"（座位空出时）。
- **方案 B**：房间即"牌桌小组"，多个牌桌并行，总在线 ≤10。

> ⚠️ **需与需求方确认**采用哪种。本文按 **方案 A** 设计（座位 + 观战席），因为它最贴合"好友娱乐、开一个房间一起玩"的实际场景。若采用方案 B，`Room` 聚合外再加一层 `Table` 概念。

**座位与观战的交互规则**（需确认后固化进 `03-游戏规则与状态机.md`）：
- 座位满员后加入者自动进观战席。
- 对局进行中**不允许中途入座**（避免破坏牌局公平），仅局间可换座。
- 观战者全程看不到任何手牌（含底牌）。

## 7. 持久化与恢复

**目标**：`pm2 restart` 不再清空所有牌局；同时为战绩/复盘打基础。

| 层 | 内容 | 频率 | 存储 |
|----|------|------|------|
| 快照 | 进行中房间的完整状态 | 每 30s 或每次阶段变更后 1s 防抖 | `data/snapshot.json`（起步）或 SQLite |
| 历史 | 每局结束后：房间、玩家、得分、局时、是否托管 | 局末写入 | SQLite `matches` / `match_players` |

**恢复流程**：进程启动 → 读快照 → 重建房间 → 重建座位（连接标为离线，等待玩家凭 token 重连）→ 定时器重新武装。

**起步建议**：用 `node:sqlite`（Node 22 内置）或 `better-sqlite3`，避免引入额外服务（阿里云免费实例不要跑 DB 服务）。

## 8. 部署拓扑（目标态）

```
        互联网
          │
   ┌──────▼──────────────────────────────┐
   │ Nginx  (80 → 301 → https)            │
   │  · 443  TLS 终结 (Let's Encrypt)     │
   │  · /            → 静态站点 client/build │
   │  · /socket.io/  → 反代 127.0.0.1:3001 │
   └──────┬──────────────────────────────┘
          │ 仅监听回环
   ┌──────▼──────────────┐
   │ pm2: ddz-server      │
   │ node src/index.js    │
   │ (单实例，状态在内存)  │
   └──────┬──────────────┘
          │
   ┌──────▼──────────────┐
   │ data/ 快照 + SQLite  │
   └─────────────────────┘
```

**为什么前端要走同域相对路径**：彻底消灭 `config.js` 里的硬编码 IP（P1-8）。前端只需 `io()`（默认连当前 origin），换服务器/上域名**零代码改动**。

**为什么 pm2 只能单实例**：状态在进程内存。若将来要 `pm2 -i max`，必须先把 Socket.IO 接 Redis adapter 并把房间状态外置 —— 记录为**扩容路径，当前不做**（10 人规模远未到瓶颈）。

**容量估算**：单个 Node 进程处理数十个 10 人房间的 Socket.IO 广播是常规量级（每房间每动作几十字节 × 10 连接）。**当前服务器的瓶颈一定不是 CPU，而是"没有 HTTPS/没有持久化"这两件事。**

## 9. 兼容与迁移策略

**不做**：一次性重写、停机迁移、数据库大改。
**要做**：**绞杀者模式（Strangler）**——新模块与旧模块并存，逐个把调用切过去。

| 步骤 | 动作 | 回滚方式 |
|------|------|----------|
| 1 | 新建 `domain/`，从 `CardLogic.js` 抽测试，行为不变 | 删目录即可 |
| 2 | 新建 `projector.js`，先在**旁路**记录"若用投影会输出什么"，与现状对比 | 关闭开关 |
| 3 | 用 `broadcast(room)` 替换裸 emit，**需覆盖全部 16 处** | git revert |
| 4 | `machine.js` 接管阶段转移，旧 `GameLogic` 方法逐个转调 | 逐个回滚 |
| 5 | `scheduler.js` 接管超时/AI，删除三份重复逻辑 | git revert |
| 6 | 前端 `GameScreen.js` 按目录拆分，每次只搬一个子区块 | 单文件回退 |

每一步都必须**单独提交、单独验证、可单独回滚**。

## 10. 未决问题（需需求方确认后固化本文）

1. **"最多 10 人"的含义** —— 房间容量（座位+观战）还是多桌并行？（第 6 节）
2. **4 人斗地主的具体规则** —— 单副牌 4 人（每人 13 张 + 底牌 4 张？）还是双副牌 108 张？当前实现是哪种？计分如何？
3. **是否需要账号体系** —— 还是维持"免注册昵称 + sessionToken"的好友娱乐形态？
4. **是否需要战绩/排行/回放** —— 决定 SQLite 表结构设计。
5. **是否接受玩家中途加入观战后上座** —— 决定 `Seat` 的换座权限模型。
6. **域名** —— 是否已有可用域名用于 HTTPS？（无域名则只能用 IP + 自签证书，微信内体验受限）
