## 2. 维护铁律（可持续优化的核心）

这五条是这套文档能"持续演进"而不是腐烂成历史垃圾的原因，**不接受例外**：

1. **代码与文档同一次提交**
   改了协议 → 改 `02-通信协议规范.md`；改了规则 → 改 `03-游戏规则与状态机.md`。不允许"先合代码，文档下次补"。

2. **每次合并必写 CHANGELOG**
   采用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 的 `新增 / 变更 / 修复 / 移除 / 安全` 五段式。写"用户能感知的变化"，不写 `fix: update code`。

3. **不可逆决策写 ADR，不写在聊天里**
   技术选型、协议破坏性变更、数据结构定型 —— 都要有一条编号 ADR，记清 *背景 / 决策 / 备选方案 / 后果*。半年后你会感谢自己。

4. **审计清单只减不增地维护**
   `00-现状审计` 里的风险项解决后**不要删行**，改为 `✅ 已修复（vX.Y.Z）` 并附修复方式。它同时是项目演进的历史账本。

5. **文档不重复代码**
   文档写"契约与意图"（接口、状态机、边界条件、为什么），不粘贴实现细节。实现细节看代码，代码看 git。

## 3. 一次功能迭代的标准流程

```
需求 → Spec（改 03/02 文档草案） → Plan（拆任务） → 实现
     → 测试（05 文档里的对应用例通过） → 更新文档 + CHANGELOG
     → ADR（如涉及决策） → Tag 发布
```

对应到实操的最小检查表（每个 PR / 每次提交前自查）：

- [ ] 玩法或协议改动，是否同步更新了 02 / 03 文档？
- [ ] 新增或修改的行为，是否在 05 文档中有对应用例，且用例已通过？
- [ ] 是否在 `CHANGELOG.md` 的 `[Unreleased]` 段落加了一行？
- [ ] 是否引入了一个"以后不好改"的决策？→ 写 ADR。
- [ ] `00-现状审计` 中若有风险项被解决，是否已标记？

- ADR 编号四位递增，文件名用中文短句，便于在文件管理器里一眼认出来。
- 日期统一 `YYYY-MM-DD`。

## 5. 术语表

| 术语 | 含义 |
|------|------|
| **座位 Seat** | 房间内可参战的固定位置，数量由玩法决定（3 人局 3 座 / 4 人局 4 座） |
| **观战席 Spectator** | 不参战但可看牌的连接，手牌对观战者一律不可见 |
| **视图裁剪 Projection** | 服务端按"谁在看"生成差异化状态，是防作弊的核心机制 |
| **权威服务端** | 客户端只发意图，全部状态变更由服务端裁定 |
| **托管 Takeover** | 玩家离线或超时后，由 AI 代为行动 |
| **阶段 Phase** | 一局内的状态机节点：叫地主 → 加倍 → 弃牌 → 出牌 → 结算 |
| **癞子 Laizi** | 可变牌的玩法开关 |
